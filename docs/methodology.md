# 경량 명세와 제한적 테스트 우선

HX Spec Harness는 요구 원문을 계약, 승인된 계획과 검사 근거에 연결합니다. **원문과 이해관계자의 실제 답변 → 목표와 수용 기준 → 질문 해결 → 계획 승인 → 작은 기대값 → 동작 실패 확인 → 최소 구현 → 관련 검사 → 독립 수용 확인 → 인계** 순서로 진행합니다. 작은 변경에서는 계획과 검사를 짧게 작성합니다. 계획 단계와 명시적 승인 기록은 생략하지 않습니다.

| 자료 | 역할 |
|---|---|
| 프로젝트 원문과 이해관계자 답변 | 목표, 경계와 수용 기준의 근거를 제공합니다. 답변을 받지 않았다면 받은 것으로 쓰지 않습니다. |
| `.harness/contract.json` | 원문 인용과 기대 결과, 구현 경로 및 검사 ID를 연결합니다. |
| `.harness/plan.json` | 목표, 범위, 수용 기준, 작업과 미해결 질문을 정리합니다. |
| `.harness/state.json` | 실제 승인 근거, 다음 작업, 설계 판단과 관찰 자기보고를 기록합니다. |
| `.harness/evidence/` | 실행한 검사의 결과와 당시 파일 판본을 기록합니다. |
| `spec`, `plan`, `status`, `brief` | 현재 계약, 계획과 근거를 읽어 보여 줍니다. 원문 해석이나 사용자 신원을 인증하지 않습니다. |

## 작업 순서

1. 원문에서 입력, 처리, 출력, 경계와 실패 조건을 읽습니다. 실제로 답한 이해관계자가 있으면 답변의 내용과 출처를 대조합니다. 그 근거로 계약의 기대 결과와 계획의 수용 기준을 작성합니다. 미래 구현 파일은 이 단계에 없어도 됩니다.
2. 결과를 바꾸는 모호함은 계획의 `questions`에 남깁니다. 질문에는 선택지와 영향을 적습니다. 실제 답변을 받은 뒤 `resolution`과 `response_source`를 기록합니다. 답변이 없으면 계획과 원문 조사를 계속하되 구현과 실행 근거는 완료로 표시하지 않습니다.
3. 사용자에게 계획을 제시하고 명시적 승인을 받습니다. 실제 승인 원문과 근거 위치가 있을 때만 `plan-approve --actor user --quote TEXT --source TEXT`를 사용합니다. 이 명령의 로컬 기록은 사용자 신원을 인증하지 않습니다. 합성 예제의 자동 승인 기록도 실제 사용자 승인 근거가 아닙니다.
4. 의미 있는 계산이나 분기에는 원문에서 독립적인 작은 입력과 기대값을 정합니다. 구현의 현재 출력을 기대값으로 복사하지 않습니다. 예를 들어 [지연 주문 합성 예제](../examples/delayed-orders/TASK.md)는 `001`과 `1`을 서로 다른 고객으로 집계합니다. 합성 예제의 값은 다른 프로젝트의 정답이 아닙니다.
5. 동작 검사가 의도한 이유로 실패하는지 확인합니다. 필요한 경우 테스트가 불러올 최소 인터페이스를 먼저 마련합니다. 기대 결과와 실제 동작이 달라서 실패하면 RED로 봅니다. 테스트 모듈 import 오류, 파일 부재, 잘못된 테스트 이름과 실행 환경 오류는 먼저 고칩니다. 이런 오류를 요구 동작의 실패 근거로 사용하지 않습니다.
6. 확인한 동작을 만족하는 최소 구현을 작성합니다. 관련 `check --id C1`을 실행하고 `status`에서 현재 판본에 유효한 근거인지 확인합니다. `command`의 종료 0은 프로세스 성공만 뜻합니다. 자동 검사와 별도로 독립적인 수용 입력 또는 기대 결과를 대조하고, 화면 요구는 실제 UI를 직접 확인합니다. 수동 관찰은 `observe`에 자기보고로 남길 수 있지만 도구가 사실을 인증하지는 않습니다.
7. `brief`와 실제 코드, 검사 로그를 대조해 입력에서 출력까지의 처리와 선택의 비용을 설명합니다. 확인한 범위와 확인하지 못한 범위를 적은 뒤 `handoff.md`에 재현 명령, 근거 위치와 다음 작업을 연결합니다. 이 문서를 생성했다는 사실만으로 인계가 끝나지는 않습니다.

같은 AI가 구현과 기대값을 함께 만들면 같은 해석 오류를 양쪽에 복제할 수 있습니다. 그래서 원문과 실제 답변을 기준으로 기대값을 별도로 검토하고, 자동 검사 외의 수용 입력 또는 실제 UI 확인을 둡니다. 전면적인 TDD 형식을 모든 문구 수정과 단순 설정 변경에 강요하지 않습니다. 의미 있는 동작 변경과 회귀 수정에서는 실패 입력과 기대 결과를 먼저 확인합니다. 구현 실패를 이유로 기대 결과를 완화하지 않습니다. 원문 해석 오류나 요구 주체의 추가 설명이 확인되면 근거를 기록하고 계획과 계약을 고친 뒤 다시 승인을 받습니다.

승인 후 계획, 계약 또는 원문이 바뀌면 기존 승인과 검사 근거는 현재 판본의 통과로 취급하지 않습니다. `check`도 검사 전후 판본을 확인하고, 실행 중 변경이 있으면 통과로 기록하지 않고 다음 검사를 중단합니다. 선언하지 않은 의존 파일의 변경이나 의도적인 기록 위조까지 막지는 못합니다.

## 참고한 원문과 이 도구의 적용

[Spec Kit의 Agentic SDD 설명](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)은 `/speckit.*` 명령의 단계와 선택적 명확화 절차를 설명합니다. [OpenSpec의 시작 안내](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md)는 자체 CLI와 `/opsx:*` 명령의 제안·적용 흐름을 설명합니다. HX Spec Harness는 그 명세와 변경 관리 개념을 참고했으며 두 제품의 CLI나 전체 절차를 설치하지 않았습니다. 이 도구에서는 사용자 요청에 따라 모든 구현 전에 계획과 명시적 승인 기록을 요구합니다. 실제 외부 스킬 원문과 이 프로젝트의 적용 차이는 [외부 원문 적용 규칙](upstream-policy.md)에 적었습니다.

이 방식이 개발 시간이나 성능을 개선한다는 효과는 측정하지 않았습니다. `spec`은 계약에 빠진 원문 요구를 찾아내지 못하고, `brief`는 코드를 자동으로 이해하지 못합니다. 실제 수용 여부는 원문, 코드, 검사 내용과 사용자의 확인을 함께 대조해야 합니다. 형식은 [계약 안내](contract.md)에, 명령의 검증 범위는 [구현 안내](implementation-guide.md)에 설명했습니다.
