# 한 과제를 끝내는 운영 순서

목표는 실제 업무 문제를 해결하고, 사용자가 구현과 검증의 이유를 설명할 수 있게 하는 것입니다. 각 단계에서는 아래 산출물만 먼저 만듭니다. 별도 문서를 계속 늘리지 않습니다. 실제 과제의 시간과 제출 규칙을 우선합니다.

| 단계 | Codex의 작업 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 발견 | 원문을 읽고 현재 업무, 대표 입력, 필요한 결과와 중요한 예외를 확인합니다. 담당자 질문은 결과를 바꾸는 2~3개씩 제시합니다. | 필수 결과를 설명할 수 있고, 중요한 정책 질문이 해결되거나 사용자가 선택을 위임했습니다. |
| 계획 | 원문과 실제 답변을 계약에 연결합니다. 필수 수용 기준, 구현 순서, 검사와 제외 범위를 계획에 적습니다. | 사용자가 실제 계획을 명시적으로 승인했습니다. |
| 첫 동작 | 입력부터 결과까지 가장 작은 필수 경로를 구현합니다. 의미 있는 계산과 분기는 작은 기대값의 실패를 확인한 뒤 구현합니다. | 핵심 입력 하나가 실제 실행에서 기대 결과를 냅니다. |
| 확장과 검증 | 승인한 예외를 구현합니다. 요구별 검사와 전체 회귀 검사를 실행합니다. UI 검사는 사용자 직접 관찰과 분리합니다. | 각 필수 요구의 통과, 실패 또는 미확인이 근거와 연결됩니다. |
| 인계 | 실행법과 핵심 처리, 선택 이유, 검사 결과와 남은 문제를 handoff.md에 적습니다. | 사용자가 제출 파일과 미확인을 확인할 수 있습니다. 실제 제출은 사용자가 수행합니다. |

## 180분 작업의 기준점

이 시간은 제안이며 실제 타이머가 기준입니다. 20분까지 질문과 계획을 정리하고, 60분까지 핵심 경로 하나를 실제 실행합니다. 120분 이후에는 새 선택 기능을 늘리지 않고 필수 요구와 예외를 확인합니다. 155분부터 실행법과 handoff를 정리합니다. 마지막 10분은 실제 제출 확인에 둡니다. 계획 승인을 기다리는 시간도 전체 시간에 포함합니다.

동작하는 결과가 없는데 문서와 스킬 선정만 계속되면 첫 동작 범위를 줄입니다. 필수 요구의 삭제나 동작 변경은 사용자의 선택이 필요합니다. 승인된 우선순위 안에서 작업 순서를 조정할 때는 같은 승인을 반복해서 받지 않습니다.

## 구현 중 사용자가 이해할 세 가지

핵심 동작이 완성될 때마다 아래 내용을 짧게 설명합니다. 사용자가 답하지 않았다고 구현을 멈추거나 이해했다고 기록하지 않습니다. 실제 서술형 단계에서는 이 설명과 도움을 중단합니다.

1. **입력에서 결과까지:** 대표 입력 하나를 사용해 검증, 계산 또는 조회, 결과 표시 순서와 담당 파일을 설명합니다.
2. **판단과 비용:** 실제로 선택한 방식 하나와 이유, 포기한 성질을 설명합니다. AI 제안과 사용자 결정을 구분합니다.
3. **검증과 한계:** 실행한 입력, 기대 결과, 실제 결과와 미확인 항목을 설명합니다. 사용자의 직접 관찰로 바꿔 서술하지 않습니다.

예를 들어 예약 데이터가 여러 행일 때 재고를 단순 결합하면 재고 수량이 중복될 수 있습니다. 예약량을 먼저 집계한 이유와 그 오류를 잡는 작은 입력을 설명하면 사용자는 계산과 검증을 함께 이해할 수 있습니다. 이 예시는 합성 설명이며 실제 과제 규칙이 아닙니다.

## 필요한 검사만 선택합니다

| 작업의 위험 | 우선 확인할 것 |
|---|---|
| 계산과 데이터 변환 | 정상 입력, 경계값, 누락과 중복, 원문 ID 및 단위 보존을 확인합니다. |
| API | 정상 요청, 잘못된 입력, 오류 상태와 반환 구조를 실제 로컬 요청으로 확인합니다. |
| SQL | 조인 카디널리티, 집계 전후 건수, NULL, 정렬과 매개변수를 확인합니다. |
| 웹 화면 | 빌드와 처리 로직을 검사합니다. 사용자는 내장 미리보기에서 성공, 빈 상태와 오류를 직접 확인합니다. 자동 UI 조작은 하지 않습니다. |
| 문구와 단순 설정 | 변경 결과와 관련 실행 경로를 직접 대조합니다. 형식을 위한 TDD를 추가하지 않습니다. |

같은 AI가 만든 코드와 테스트만 대조하면 해석 오류가 함께 남을 수 있습니다. 원문에서 별도로 정한 수용 입력을 사용합니다. 허용된 환경에 독립 검토자가 있으면 원문과 구현의 차이를 검토하게 합니다. 없으면 별도 검토 순서로 원문을 다시 대조하고 독립 에이전트 검토라고 쓰지 않습니다.

## 문맥이 끊겼을 때

`status`와 `plan`, 최신 handoff를 읽습니다. 완료 보고만 보고 다음 작업을 시작하지 않습니다. 현재 파일에서 검사 근거가 유효한지 확인합니다. `next --text`에는 바로 실행할 다음 작업과 막힌 조건을 적습니다. 오래된 계획과 증거가 표시되면 변경 원인을 확인한 뒤 필요한 승인과 검사를 갱신합니다.
